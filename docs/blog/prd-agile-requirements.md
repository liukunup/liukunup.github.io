## 概述

需求拆解是把"用户想要的"变成"开发能做的"的过程。

- **IPD 需求线**：自上而下，流程驱动，阶段门控
- **敏捷需求线**：自下而上，用户驱动，迭代交付

## 需求拆解全景对比

```
IPD 线：          敏捷线：
需求提出          Epic（史诗）
    ↓                ↓
IR（初始需求）    Feature（特性）
    ↓                ↓
SR（系统需求）    User Story（用户故事）
    ↓                ↓
AR（分配需求）    Task（任务）
    ↓
开发任务
```

## 一、IPD 需求拆解线

### 拆解流程

```
SF（系统特性）
    ↓ 分解
IR（初始需求）
    ↓ 分解
SR（系统需求）
    ↓ 分解
AR（分配需求）
    ↓ 分配
开发任务
```

### 各层级说明

| 层级 | 说明 | 视角 | 输出物 |
|------|------|------|--------|
| **SF** | 系统特性，产品卖点和亮点 | 市场/销售 | 产品包定义 |
| **IR** | 初始需求，客户/市场视角 | 客户 | 需求规格书 |
| **SR** | 系统需求，研发视角，可测试 | 研发 | 系统规格书 |
| **AR** | 分配需求，分到子系统/模块 | 子系统 | 子系统规格 |

### 拆解示例：网上商城

```
SF：全渠道销售体系
    ↓
IR：建立网上商城，减少客流流失
    ↓
SR：
├── SR1：用户可以浏览商品
├── SR2：用户可以下单支付
└── SR3：订单可跟踪配送
    ↓
AR：
├── AR1-1：商品展示模块
├── AR1-2：搜索模块
├── AR2-1：购物车模块
├── AR2-2：支付模块
└── AR3-1：订单模块
```

### 关键规则

| 规则 | 说明 |
|------|------|
| **状态卷积** | 下级状态自动向上级卷积 |
| **AR 最小单位** | AR 不可再分解，可复制新建 |
| **变更控制** | 严格变更流程，EC 审批 |

## 二、敏捷需求拆解线

### 拆解流程

```
Epic（史诗）
    ↓ 拆解
Feature（特性）
    ↓ 拆解
User Story（用户故事）
    ↓ 拆解
Task（任务）
```

### 各层级说明

| 层级 | 说明 | 周期 | 原则 |
|------|------|------|------|
| **Epic** | 战略愿景，大型需求 | 数月 | 不可直接开发 |
| **Feature** | 业务功能，可交付特性 | 数周 | 可跨 Sprint |
| **Story** | 用户价值，可一个 Sprint 完成 | 1 Sprint | INVEST 原则 |
| **Task** | 开发任务 | 1 天内 | 动词描述 |

### 拆解示例：网上商城

```
Epic：建立全渠道销售体系
    ↓
Feature：
├── F1：商品管理
├── F2：会员管理
├── F3：订单管理
└── F4：支付管理
    ↓
Story：
├── F1-1：用户可以搜索商品
├── F1-2：用户可以查看商品详情
├── F2-1：用户可以注册会员
├── F2-2：用户可以积分兑换
├── F3-1：用户可以加入购物车
└── F3-2：用户可以下单支付
    ↓
Task：
├── 任务1：实现搜索 API
├── 任务2：实现搜索页面
└── 任务3：编写搜索测试用例
```

### User Story 标准格式

```
作为 [角色]，我 [想要] [功能]，以便 [目标]
```

### INVEST 原则

| 字母 | 含义 | 说明 |
|------|------|------|
| **I** | Independent | 独立的，尽量无依赖 |
| **N** | Negotiable | 可协商的，不是固定规格 |
| **V** | Valuable | 有价值的，对用户有意义 |
| **E** | Estimable | 可估算的，团队能评估 |
| **S** | Small | 小的，一个 Sprint 完成 |
| **T** | Testable | 可测试的，有验收标准 |

### 验收标准写法（Given-When-Then）

```
Given  用户已登录
When  点击"加入购物车"
Then  商品出现在购物车列表
And   显示成功提示
```

## 三、两条线核心对比

| 维度 | IPD 拆解线 | 敏捷拆解线 |
|------|-----------|-------------|
| **方向** | 自上而下 | 自下而上（Story 驱动 Epic） |
| **驱动力** | 流程/阶段门控 | 用户价值/迭代 |
| **颗粒度** | 粗 → 细 | 细 → 粗 |
| **变更** | 严格审批 | 拥抱变化 |
| **交付** | 阶段式（大批量） | 迭代式（小批量） |
| **文档** | 详细规格书 | 轻量故事卡 |

## 四、拆解方法对比

### IPD：功能分解法

```
系统功能
    ├── 子系统1
    │   ├── 模块1
    │   └── 模块2
    └── 子系统2
        ├── 模块3
        └── 模块4
```

**特点**：按系统结构分解，职责清晰

### 敏捷：用户价值分解法

```
用户目标
    ├── 场景1
    │   ├── 行为1 → Story
    │   └── 行为2 → Story
    └── 场景2
        ├── 行为3 → Story
        └── 行为4 → Story
```

**特点**：按用户价值分解，用户视角

## 五、何时用哪条线

| 项目特征 | 推荐 |
|----------|------|
| 大型硬件/复杂系统 | IPD 拆解线 |
| 软件/互联网产品 | 敏捷拆解线 |
| 跨部门协作多 | IPD 拆解线 |
| 小团队快速响应 | 敏捷拆解线 |
| 需求稳定 | IPD 拆解线 |
| 需求变化频繁 | 敏捷拆解线 |
| 需要详细文档 | IPD 拆解线 |
| MVP 快速验证 | 敏捷拆解线 |

## 六、混合使用

实际项目中可以根据需要混合使用：

| 场景 | 使用方式 |
|------|----------|
| 硬件 + 软件产品 | IPD 为主，敏捷辅助 |
| 大型软件项目 | IPD 规划版本，敏捷执行 Sprint |
| 产品规划层 | Epic/Feature |
| 项目执行层 | User Story/Task |

## 总结

| | IPD 拆解线 | 敏捷拆解线 |
|---|-----------|-------------|
| **术语** | SF → IR → SR → AR | Epic → Feature → Story → Task |
| **拆解方式** | 功能分解（系统结构） | 价值分解（用户视角） |
| **适合** | 硬件、复杂系统 | 软件、互联网产品 |
| **优势** | 规范、可追溯 | 灵活、响应快 |
