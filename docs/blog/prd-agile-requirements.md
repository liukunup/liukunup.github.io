## 概述

在产品开发过程中，需求管理是连接业务与技术的桥梁。不同的开发模式（IPD 瀑布式 vs 敏捷迭代）有不同的需求术语体系，但核心目标一致：**把模糊的用户诉求转化为可交付的产品功能**。

本文系统梳理 PRD（产品需求文档）体系和敏捷开发中的需求术语链条，并与 IPD 体系进行横向对照，帮助产品经理建立完整的术语认知框架。

## PRD 需求术语链条

PRD 体系的需求从"模糊"到"具体"层层递进，更强调**用户价值**和**可交付性**：

```
用户痛点 → 解决方案 → Epic → Feature → User Story → Acceptance Criteria
```

### 需求层级详解

| 层级 | 说明 | 典型周期 | 价值定位 |
|------|------|----------|----------|
| **用户痛点** | 用户面临的真实问题或困扰 | 持续收集 | 战略价值 |
| **解决方案** | 解决痛点的思路和方向 | 数周至数月 | 业务价值 |
| **Epic** | 可交付的解决方案包 | 数月 | 战略/业务价值 |
| **Feature** | 客户可感知的产品功能 | 数周至多 Sprint | 业务价值 |
| **User Story** | 从用户角度描述的具体功能 | 一个 Sprint 内 | 用户价值 |
| **Acceptance Criteria** | 验收标准，功能完成的定义 | - | 交付价值 |

## Epic、Feature、Story、Task 详解

### Epic（史诗）

Epic 是项目的愿景目标，具有战略价值。通过 Epic 的落地达成，使公司可以获得相应的市场地位和回报。

**特征：**
- 颗粒度大，通常需要数月完成
- 战略层面，关注整体目标
- 可拆分为多个 Feature

**示例：**
```
作为[网上商城]，我希望建立全渠道销售体系，
以便减少门店消费者流失，保有市场份额
```

### Feature（特性）

Feature 是可带来价值的产品功能和特性。相比 Epic，Feature 更具体、更形象，客户可以感知，具有业务价值。

**特征：**
- 通常需要数周，多个 Sprint 完成
- 具有明确的业务价值
- 可拆分为多个 User Story

**示例：**
```
会员管理功能
促销管理功能
订单管理功能
配送管理功能
```

### User Story（用户故事）

User Story 是从用户角度对产品功能的详细描述，符合 INVEST 原则，通常在一个 Sprint 中完成。

**INVEST 原则：**

| 字母 | 含义 | 说明 |
|------|------|------|
| **I** | Independent | 独立的，避免与其他故事强依赖 |
| **N** | Negotiable | 可协商的，不是固定规格 |
| **V** | Valuable | 有价值的，对用户或业务有意义 |
| **E** | Estimable | 可估算的，团队能评估工作量 |
| **S** | Small | 小的，可在一个 Sprint 完成 |
| **T** | Testable | 可测试的，有明确的验收标准 |

**标准格式：**

```markdown
作为 [角色]，我 [想要] [某个功能]，以便 [实现某个目标]
```

**示例：**

```
作为管理员，我能够进行会员的积分管理，
以便于划分消费等级提供不同增值服务

作为购物者，我希望将商品加入心愿单，
以便于日后购买

作为项目经理，我希望生成项目状态报告，
以便向利益相关者同步项目进展
```

### Task（任务）

Task 是团队成员要完成的具体任务，是 Story 的进一步细分，通常在一天内完成。

**Story vs Task 的区别：**

| 维度 | Story | Task |
|------|-------|------|
| **关注点** | 聚焦价值 | 聚焦实现 |
| **时间跨度** | 数天，一个 Sprint | 数小时，最多一天 |
| **描述** | 名词形式 | 动词形式 |
| **原则** | INVEST | 具体可执行 |

**示例：**
```markdown
Story: 作为管理员，我能够进行会员的积分管理

Task 分解:
├── 业务逻辑开发
├── 积分规则设计
└── 积分数据库设计
```

## 用户故事 3C 原则

用户故事的 3C 指的是**卡片（Card）、对话（Conversation）、确认（Confirmation）**：

1. **Card**：对用户故事的书面描述
2. **Conversation**：团队成员之间为明确需求细节而展开的讨论
3. **Confirmation**：定义用户故事何时完成的验收标准

### 验收标准写法

**Good：**
```markdown
Given 用户已登录系统
When 用户点击"加入心愿单"按钮
Then 商品应出现在"我的心愿单"列表中
And 系统显示成功提示
And 页面刷新后数据保持
```

**Bad：**
- "功能正常" ❌
- "用户体验良好" ❌
- "满足用户需求" ❌

> 如果写不出验收标准，说明需求本身尚未想清楚。

## PRD 与 IPD 需求术语对照

| PRD/敏捷术语 | IPD 术语 | 颗粒度 | 关注点 |
|-------------|----------|--------|--------|
| Epic（史诗） | Charter（任务书） | 战略层 | 愿景目标 |
| Feature（特性） | Requirement（需求） | 业务层 | 功能特性 |
| User Story（用户故事） | HLR/LLR | 交付层 | 可执行需求 |
| Task（任务） | Work Item（工作项） | 执行层 | 具体任务 |
| Backlog（待办列表） | PTS（产品跟踪系统） | 管理面 | 需求池 |

### 核心差异

| 维度 | PRD/敏捷 | IPD |
|------|-----------|-----|
| **核心理念** | 以用户为中心 | 以流程为中心 |
| **交付方式** | 迭代交付 | 阶段门控 |
| **需求变化** | 拥抱变化 | 变更控制 |
| **文档形式** | 轻量级故事卡 | 厚重规格文档 |

## 用户故事地图（User Story Mapping）

用户故事地图是一种协作技术，用于将用户故事组织成二维地图。

### 地图结构

```
横轴：用户旅程（骨干）
纵轴：优先级
```

### 核心概念

| 概念 | 说明 |
|------|------|
| **骨干（Backbone）** | 用户旅程中的高层级活动 |
| **行走骨架（Walking Skeleton）** | MVP 版本所需的最少故事集 |
| **发布切片（Release Slices）** | 每个版本包含的故事 |
| **深度（Depth）** | 从核心到边缘的完整功能范围 |

### 映射步骤

1. **定义用户和目标**：明确"为谁映射"和"他们试图实现什么"
2. **构建叙事骨干**：按时间顺序映射高层级活动
3. **识别任务**：列出每个活动下的具体任务
4. **编写用户故事**：为每个任务编写具体故事
5. **优先级排序**：划分发布切片
6. **识别差距**：检查遗漏的功能和问题

### 示例：电商用户故事地图

```
用户购物流程
├── 浏览商品
│   ├── 搜索商品
│   ├── 查看详情
│   └── 比价功能（可选）
├── 加入购物车
│   ├── 选择数量
│   ├── 使用优惠券
│   └── 修改规格
├── 下单支付
│   ├── 选择地址
│   ├── 选择支付方式
│   └── 确认订单
└── 订单管理
    ├── 查看订单
    ├── 取消订单
    └── 申请售后
```

## PRD 文档结构

一份完整的 PRD 通常包含以下章节：

```markdown
# 产品需求文档

## 1. 概述
   - 背景与目的
   - 目标用户
   - 范围与边界

## 2. 用户需求
   - 用户画像
   - 用户痛点
   - 使用场景

## 3. 功能需求
   - 功能列表
   - 功能详述
   - 用户故事

## 4. 非功能需求
   - 性能要求
   - 安全要求
   - 兼容性要求

## 5. 验收标准
   - 功能验收条件
   - 测试用例

## 6. 风险与依赖
   - 技术风险
   - 业务依赖
   - 外部依赖

## 7. 附录
   - 术语表
   - 参考资料
```

## 敏捷需求管理 DEEP 原则

产品待办列表（Product Backlog）应遵循 DEEP 原则：

| 字母 | 含义 | 说明 |
|------|------|------|
| **D** | Detailed appropriately | 适当详细，近期需求详细，远期需求粗略 |
| **E** | Estimated | 已估算，每个条目都有工作量估算 |
| **E** | Emergent | 涌现的，持续演进，随时可以添加新需求 |
| **P** | Prioritized | 已排序，按优先级排列 |

## 常见痛点与解决

### 痛点 1：用户故事写不下去

76% 的敏捷团队认为"用户故事写不下去"是主要痛点，但仅有 11% 源于格式不熟悉，其余多与**需求拆分不清、验收标准缺失**相关。

**解决方案：**
- 先写验收标准，再写用户故事
- 拆分过大的 Epic 为多个 Feature
- 识别隐含假设和依赖

### 痛点 2：需求变更频繁

敏捷拥抱变化，但无序变更会影响进度。

**解决方案：**
- 建立 Product Backlog 优先级机制
- 明确"完成"（Done）的定义
- Sprint 期间原则上不接受新需求

### 痛点 3：跨团队协作困难

**解决方案：**
- 定期开展用户故事地图工作坊
- 保持 Product Owner 与团队的持续沟通
- 使用共同语言（用户故事）而非技术术语

## PRD vs 用户故事：如何选择

| 场景 | 推荐方式 |
|------|----------|
| 探索性阶段 | 用户故事（轻量灵活） |
| 复杂功能开发 | PRD + 用户故事 |
| 法规合规需求 | 详细 PRD |
| MVP 快速验证 | 用户故事 |
| 大型瀑布项目 | 详细 PRD |
| 敏捷迭代项目 | 用户故事 |

## 总结

PRD 体系和敏捷需求管理是一套完整的术语框架，从用户痛点到可执行的用户故事，层层递进：

1. **Epic** 定义战略愿景
2. **Feature** 拆解业务功能
3. **User Story** 落地用户价值
4. **Acceptance Criteria** 明确完成标准
5. **User Story Map** 可视化整体规划

与 IPD 体系相比，PRD 更强调**用户价值**和**快速迭代**，而 IPD 更强调**流程管控**和**风险前置**。两者各有优势，实际工作中可根据项目特点灵活选用。
