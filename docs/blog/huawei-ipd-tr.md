## 概述

在硬件研发领域，最"昂贵"的问题往往是：**在该冻结时没冻结、在该验证时没验证、在该拒绝时没拒绝**。需求理解偏差、接口假设失真、DFx 缺位，最终在试产或量产阶段集中爆雷。

华为 IPD（集成产品开发）体系中的**技术评审（Technical Review，TR）**正是解决这一问题的核心机制——通过结构化的评审流程、量化的准入/准出标准、证据驱动的决策机制，把研发从"靠经验推进"升级为"靠证据决策"。

## TR 的本质：技术闸门，而非汇报会

很多人把 TR 理解为"技术评审会议"，这只对了一半。更准确的定义是：

> **TR = 技术成熟度关口判定 + 下一阶段授权 + 风险承诺签署**

可以把 TR 看作"技术侧的 Gate"：
- **输入**：阶段交付物 + 证据包（Evidence Package）
- **标准**：入口/出口条款（Entry/Exit Criteria）
- **输出**：结论 + 通过条件 + 风险与行动项闭环

### 评审结论类型

| 结论 | 含义 | 后续行动 |
|------|------|----------|
| **Go** | 完全通过，可进入下一阶段 | - |
| **Conditional Go** | 有条件通过，需在限定时间内完成整改 | 需绑定豁免条款（Waiver） |
| **Recycle** | 不通过，需返工 | 重新准备后再次评审 |
| **Hold** | 暂停，等待更多信息或资源 | - |
| **Kill** | 终止项目 | - |

## 华为 IPD 中的 7 个技术评审点

华为 IPD 明确定义了 **7 个技术评审点（TR1-TR6，其中 TR4 包含 TR4A）**，每个 TR 都有明确的准入与准出条件。

### TR 评审全景图

| 评审点 | 阶段 | 评审重点 | 核心关注 |
|--------|------|----------|----------|
| **TR1** | 概念阶段 | 需求与概念评审 | 需求完整性、概念方案合理性、技术可行性 |
| **TR2** | 计划阶段 | 系统架构评审 | 架构合理性、模块划分、接口定义 |
| **TR3** | 计划阶段 | 详细设计评审 | 模块设计、接口设计、数据库设计 |
| **TR4** | 开发阶段 | 详细设计和单元测试评审 | 代码质量、单元测试、模块集成效果 |
| **TR4A** | 开发阶段 | 系统设计验证（SDV） | 原型机功能验证、系统规格实现 |
| **TR5** | 验证阶段 | 系统测试（SIT） | 功能、性能、可靠性、安全性测试 |
| **TR6** | 验证阶段 | β测试评审 | 可靠性验证、用户验收、缺陷闭环 |

### TR4 的准确含义

在华为标准中，**TR4 对应"详细设计和单元测试"评审**，重点关注：
- 代码是否符合设计规范
- 单元测试覆盖率是否达标
- 模块间接口是否正确
- 文档是否完整更新

## 系统级测试的细分

华为 IPD 对系统级测试有明确的定义和分层：

| 测试类型 | 缩写 | 目的 | 说明 |
|----------|------|------|------|
| **系统设计验证** | SDV | 验证系统功能规格是否实现 | 针对产品原型机 |
| **系统集成测试** | SIT | 验证系统功能、性能、可靠性等 | 针对初试产品 |
| **系统验证测试** | SVT | 验证制造流程和设计完整性 | 必须在产线正式生产出的硬件上执行 |

### 测试分层示意

```
SDV → 原型机验证（"能不能做出来"）
   ↓
SIT → 初试产品验证（"做得对不对"）
   ↓
SVT → 量产验证（"能不能稳定生产"）
```

## Entry/Exit 标准：TR 的灵魂

很多 TR 失败，是因为标准写得像口号："设计基本完成""风险可控"。这种句子无法判定，也无法审计。

### 条款写法模板

> **条款 = 动词 + 对象 + 判定方式 + 证据形态**

**优秀案例：**
- "关键需求覆盖率 ≥95%（**证据**：需求-用例追溯矩阵/链接）"
- "关键接口已冻结（**证据**：ICD版本 + 变更记录）"
- "试产测试准备就绪（**证据**：治具清单 + 校准记录 + 脚本版本库）"

**反面教材：**
- "设计基本完成" ❌
- "风险可控" ❌
- "测试情况良好" ❌

## TR Package 证据包模板

TR Package 的关键不是"写得多"，而是"证据能被追溯、能被复核"。建议固化以下结构：

```markdown
TR Package 目录：
├── 1. 项目概览（目标/范围/版本/里程碑偏差）
├── 2. 阶段交付物清单（完成度 + 证据链接 + 阻塞项）
├── 3. 需求与范围基线（变化点 + 影响评估）
├── 4. 系统架构与关键接口（ICD状态、兼容策略）
├── 5. 关键技术成熟度证据（原型/实验数据/性能边界）
├── 6. 验证与测试证据（覆盖率、缺陷分布、未关闭项）
├── 7. DFx评估（DFM/DFT/DFA、工艺窗口、治具策略）
├── 8. 可靠性与合规（试验矩阵、认证路线）
├── 9. 供应链与成本风险（长周期料、二供、备料策略）
├── 10. 风险清单与对策（Top风险：触发条件+缓解+验证）
├── 11. 待决策问题（需要评审委员会拍板的关键取舍）
└── 12. 行动项清单（预置：Owner/Due/验收证据/关闭标准）
```

## TR 全流程怎么跑

### 会前：定义评审范围、结论类型与"不可妥协条款"

1. **评审范围**：本次 TR 覆盖哪些子系统/关键特性
2. **结论类型**：Go / Conditional Go / Recycle / Hold / Kill
3. **不可妥协条款（Hard Gate）**：
   - 法规合规路径未明确
   - 关键安全需求没有验证计划
   - 关键长周期料无备选方案

### 会中：把会议做成"判定系统"

**三条规则：**

1. **先对照 Exit 标准，再讨论如何补齐**——否则容易陷入"讨论很充分，但不知道是否过关"

2. **以证据作为共同语言**——凡是没有证据的结论，都必须转换成行动项

3. **Conditional Go 必须绑定豁免条款（Waiver）**：
   - 豁免条款是什么、风险是什么
   - 如何监控、何时必须关闭
   - 超期如何升级

### 会后：两件事决定 TR 成败

**1. 关口签署（固定纪要字段）**

```markdown
TR 纪要固定字段：
- 评审结论：Go / Conditional Go / Recycle / Hold / Kill
- 通过条件（如有）：必须在 X 日前关闭哪些条款
- 豁免条款（如有）：风险承诺、监控方式、升级机制
- 基线版本：需求/架构/ICD/BOM/测试策略版本号
- 行动项清单：Owner / Due / 验收证据 / 关闭标准
```

**2. 闭环审计（T+7 / T+14 的"抽检式复核"）**

重点抽检两类：
- 关键风险项是否进入受控闭环
- 证据是否真实有效（不是"写了报告但没有数据"）

## 不同阶段 TR 该评什么

| 阶段 | 类似评审 | 核心问题 |
|------|----------|----------|
| 概念/立项 | SRR | 需求可信、边界清晰、风险可陈述 |
| 方案/计划 | PDR | 架构合理、接口受控、关键假设有证据 |
| 详细设计 | CDR | 可实现、可制造、可测试 |
| 集成测试前 | TRR | 测试准备就绪、数据可采、缺陷门禁清晰 |
| 试产/量产前 | PRR | 生产准备就绪、质量控制可执行、供应链可兑现 |

## TR 最关键的 10 个检查维度

1. **需求质量**：需求是否可验证？是否有验收标准与边界？
2. **端到端追溯**：关键需求是否能追到设计与测试证据？
3. **关键假设显性化**：性能边界、环境条件、制造能力假设是否写清？
4. **接口与集成风险**：接口是否冻结？跨供应商接口如何验收？
5. **技术成熟度证据**：关键技术点有没有数据，而不是信心？
6. **DFx（可制造/可测试/可维护）**：可测试性是否覆盖关键失效模式？
7. **可靠性与合规**：可靠性指标如何分解？认证路线是否清晰？
8. **供应链韧性**：长周期料识别了吗？二供/替代料认证计划可执行吗？
9. **变更控制**：重大变更是否评估影响并经批准？
10. **风险与行动项闭环**：Top风险是否都有"触发条件+缓解+验证"？

## 常见评审失效模式

### 1. 评审变成"汇报会"

项目组讲进展、专家点评、纪要很长，但缺少两件决定性的东西：
- **可判定的出口标准**（达到/未达到，不靠感觉）
- **明确的关口结论**（通过/返工/暂停/终止）

### 2. 风险发现得太晚

工程管理里有一个朴素但残酷的规律：**缺陷发现越晚，修复成本越高**。

对硬件而言，这种放大不仅体现在研发工时，还体现在：
- 重打样
- 重新认证
- 供应链备料报废
- 产线节拍重算
- 客户侧返修与品牌损失

### 3. 跨部门对齐失败

研发说"功能通了"，制造问"可测试吗？节拍算过吗？"，质量问"证据链在哪？"，供应链问"关键料有二供吗"？

如果 IPD 阶段评审没有共同语言（条款库/证据形态/结论规则），就会退化成"谁嗓门大听谁的"。

## 让 TR 变成组织能力

### 1. 标准化"条款库与证据形态"

评审委员会可以换人，但条款库、证据包、签署机制必须稳定。

### 2. 把委员会做"轻"，把规则做"硬"

硬规则包括：
- 资料预审不过不进会
- Hard Gate 不满足原则上不得 Go
- Conditional Go 必须绑定豁免条款与升级机制

### 3. 用数据衡量 TR 有效性

| 指标 | 低值含义 |
|------|----------|
| 行动项按期关闭率 | 执行力与验收机制不足 |
| 行动项复开率 | 标准不清或证据质量差 |
| TR 后逃逸缺陷 | 关键风险前移不足 |
| 试产良率/返修工时趋势恶化 | DFx/测试准备/供应链问题未被闸门拦住 |

## 总结

IPD 技术评审（TR）真正的价值，不在于材料有多漂亮，而在于把研发推进从"靠经验与乐观"转为"靠标准与证据"。

当你建立起 **Entry/Exit 标准、证据包、关口结论、豁免规则与闭环审计**，TR 就不会再是项目负担，而会沉淀为组织能力：**更早暴露风险、更少返工、更稳定交付**，推动研发体系从"流程合规"走向"治理有效"。
