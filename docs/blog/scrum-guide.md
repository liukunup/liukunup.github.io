## 概述

Scrum 是最流行的敏捷开发框架，通过**经验主义过程**（透明、检视、适应）为复杂问题带来秩序。

## 什么是 Sprint？

**Sprint（冲刺）**是 Scrum 的核心，是一个固定时长的迭代周期，通常 1-4 周。

**简单理解**：
- 把一个大项目拆成多个小阶段
- 每个阶段固定时间（如 2 周）
- 每个阶段都要产出可用的产品增量

**类比**：
```
传统方式：9 个月完成项目交付
Sprint 方式：第1个月 第2个月 第3个月 ...
           ┌─────┐ ┌─────┐ ┌─────┐
           │增量1│ │增量2│ │增量3│ ...
           └─────┘ └─────┘ └─────┘
           ↑每月交付可用功能
```

**Sprint 的特点**：

| 特点 | 说明 |
|------|------|
| **固定时长** | 长度一旦确定，整个项目保持不变 |
| **时间盒** | 长度固定，工作量自适应 |
| **不可中断** | Sprint 期间目标不变 |
| **产出增量** | 每个 Sprint 都要交付可用功能 |

**Sprint 长度选择**：

| 团队类型 | 推荐长度 | 原因 |
|----------|----------|------|
| 互联网/创业 | 1 周 | 快速响应市场 |
| 企业软件 | 2 周 | 平衡速度和稳定性 |
| 复杂系统 | 3-4 周 | 需要更多时间消化 |

> 原则：**越复杂，未知越多，Sprint 应越短**

**Sprint 能做什么**：

```
Sprint 1: 用户登录 + 注册        → 上线
Sprint 2: 商品浏览 + 搜索        → 上线
Sprint 3: 购物车 + 下单          → 上线
Sprint 4: 支付功能              → 上线
...                           → 持续交付
```

> 每个 Sprint 结束后，用户都能用到新功能

## 一、三个角色

| 角色 | 职责 | 核心工作 |
|------|------|----------|
| **产品负责人** | 价值最大化 | 管理产品待办列表，排序优先级 |
| **Scrum Master** | 服务型领导 | 辅导团队，清除障碍，优化流程 |
| **开发团队** | 跨职能自组织 | 交付产品增量 |

### 产品负责人（PO）

- 管理产品待办列表
- 排序优先级，确保价值最大化
- 与利益相关者沟通

> PO 不一定是产品经理，核心是确保团队交付价值

### Scrum Master

- 辅导团队 Scrum 实践
- 清除障碍
- 优化流程
- 组织 Scrum 仪式

### 开发团队

- 5-7 人（双披萨原则）
- 跨职能自组织
- 共同对交付负责

## 二、三个工件

| 工件 | 说明 |
|------|------|
| **产品待办列表** | 产品所有需求的排序列表 |
| **冲刺待办列表** | 当前 Sprint 要完成的工作 |
| **增量** | Sprint 产出的可用产品 |

### 产品待办列表

- 产品负责人维护
- 按价值排序
- 持续更新
- 包含：功能、优化、缺陷修复

### 冲刺待办列表

- Sprint 规划时从产品待办列表选取
- Sprint 期间可调整
- 团队承诺完成

## 三、五个事件

| 事件 | 时长 | 目的 |
|------|------|------|
| **Sprint** | 1-4 周 | 固定迭代周期 |
| **Sprint 规划** | 2-8 小时 | 规划 Sprint 工作 |
| **每日站会** | 15 分钟 | 同步进展，清除障碍 |
| **Sprint 评审** | 1-4 小时 | 展示增量，收集反馈 |
| **Sprint 回顾** | 1-3 小时 | 反思改进 |

### Sprint 规划

**回答两个问题：**

1. **做什么？** - 从产品待办列表选取
2. **怎么做？** - 拆解为任务

**输入**：产品待办列表、Sprint 目标
**输出**：冲刺待办列表

### 每日站会

**三个问题：**

- 我昨天做了什么？
- 我今天计划做什么？
- 有什么阻碍？

> 15 分钟内，站会不是进度汇报会

### Sprint 评审

- 演示完成的增量
- 收集利益相关者反馈
- 产品负责人决定是否发布

### Sprint 回顾

- 团队一起反思
- 什么做得好？
- 什么可以改进？

## 五、Scrum 价值观

| 价值观 | 说明 |
|--------|------|
| **承诺** | 承诺能完成的工作 |
| **勇气** | 敢于面对困难，说出真相 |
| **专注** | 聚焦 Sprint 目标 |
| **开放** | 工作和过程对所有人开放 |
| **尊重** | 尊重他人，相互支持 |

## 六、Sprint 执行要点

### Sprint 长度选择

| 产品类型 | 推荐 Sprint 长度 |
|----------|------------------|
| 互联网产品 | 1-2 周 |
| 企业软件 | 2-4 周 |
| 复杂系统 | 4 周 |

> 越复杂，未知越多，Sprint 应越短

### 团队容量估算

- 基于历史速度
- 估算 Stories 数量
- 留出缓冲

### 变更处理

- Sprint 期间不加入新需求
- 紧急变更需结束当前 Sprint
- 变更反馈到产品待办列表

## 七、Scrum vs 敏捷

| 维度 | 敏捷 | Scrum |
|------|------|-------|
| 定位 | 理念/价值观 | 具体框架 |
| 实践 | 指导原则 | 明确规则 |
| 适用范围 | 广泛 | 软件开发为主 |

## 八、Scrum vs 看板

| 维度 | Scrum | 看板 |
|------|-------|------|
| 周期 | 固定 Sprint | 持续流动 |
| 角色 | 明确三种角色 | 无强制角色 |
| 仪式 | 有 | 无强制 |
| 适用 | 产品开发 | 运维/支持 |

## 九、常见问题

### Q: Sprint 完不成怎么办？

1. 分析原因（估算不准？阻塞太多？）
2. 调整容量
3. 回顾中改进

### Q: 需求变更怎么办？

1. 放入产品待办列表
2. PO 重新排序
3. 下个 Sprint 再做

### Q: PO 和 SM 能是一个人吗？

- 不建议
- PO 关注价值
- SM 关注流程
- 职责分离

## 十、Scrum 检查清单

### Sprint 规划检查

- [ ] 有明确的 Sprint 目标
- [ ] 团队承诺可完成
- [ ] 任务已分解
- [ ] 团队成员认领任务

### 每日站会检查

- [ ] 15 分钟内
- [ ] 聚焦 Sprint 目标
- [ ] 识别阻塞
- [ ] 不讨论细节

### Sprint 评审检查

- [ ] 演示可用增量
- [ ] 收集反馈
- [ ] 更新产品待办列表

### Sprint 回顾检查

- [ ] 团队全员参与
- [ ] 讨论做得好的
- [ ] 讨论需改进的
- [ ] 制定改进措施

## 总结

Scrum 核心：**3 角色 + 3 工件 + 5 事件 + 5 价值观**

```
角色：PO / SM / 开发团队
工件：产品待办 / 冲刺待办 / 增量
事件：规划 / 站会 / 评审 / 回顾
价值观：承诺 / 勇气 / 专注 / 开放 / 尊重
```
